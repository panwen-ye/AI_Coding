EOS Test Agent POC 架构设计与可执行改造方案

项目定位： 不是简单的 AI 自动写测试，而是通过 Agent 将没有文档、没有测试的 EOS 老系统逆向还原为可验证的业务行为模型，为后续 Spring Boot + Vue 现代化改造提供安全基础。

一、POC目标

选择一个 EOS 中等复杂业务模块（例如订单模块），完成：

  • 代码分析
  • 数据库分析
  • 业务规则抽取
  • 业务场景生成
  • Runtime行为采集
  • Golden Master建立
  • OpenSpec生成
  • 测试自动生成

核心Skill职责

  • Code Archaeology：建立代码调用关系和依赖图。
  • DB Analysis：分析表、字段、存储过程、Trigger。
  • Business Rule：从代码和运行结果中提取业务规则。
  • Runtime Probe：记录EOS真实输入输出和数据库变化。
  • Golden Master：保存旧系统行为基线。
  • Reviewer：审查AI推断，降低幻觉风险。

七、关键风险

  • EOS环境无法完整恢复。
  • 动态调用导致静态分析不足。
  • 业务规则存在歧义。
  • Oracle状态难以重复。
  • LLM上下文成本过高。
解决原则： AST保证事实，Runtime保证行为，LLM负责解释，人负责最终确认。

八、成熟案例参考方向

  • IBM watsonx Code Assistant：企业级Java现代化、代码理解和测试生成。
  • OpenRewrite / Moderne：基于AST的确定性Java迁移。
  • AWS Strangler Fig：新旧系统并存、渐进式替换。
  • Diffblue：AI生成Java测试。
